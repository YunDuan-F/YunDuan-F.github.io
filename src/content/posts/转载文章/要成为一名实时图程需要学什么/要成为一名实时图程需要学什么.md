经常被问，需要了解什么才能做图形程序员。是时候写篇文章来放链接，而不是每次都再打一遍了。

我们正处于LLM的奇怪时期。我认为目前的ML配不上市场炒作，未来几年大众热度会从ML上转移一些。感觉那些投机骗子下一步会转向量子计算，或者找别的什么东西炒作套利。不过，ML本身在计算机科学工具箱里确实有用，个人觉得学习它提供的拟合与优化技术是有价值的。做了个可以了解ML底层内容的视频，学与否看你情况：   
[Machine Learning For Game Developers](https://www.youtube.com/watch?v=sTAqWRsEiy0)

除此之外
现代渲染可以说是两份工作合二为一：  
1. 学习CPU端 —— 即学习DirectX12、Vulkan、Metal或类似的现代‘显式’API，以及用于支持加载资源及其他辅助任务的引擎编程。  
2. 学习GPU端 —— 即现代光照与着色的数学原理，诸如阴影、环境光遮蔽和后期处理效果之类的渲染技术。此外，充分理解GPU上各类操作的执行效率差异，对于掌握如何优化程序以提升其实时运行性能而言至关重要。

同时学习这两样东西比较困难，如果想专注于#2，则可在#1采用较为简单的实现方案，例如OpenGL、WebGL、DirectX11、现成的引擎或者类似的工具。若想专注于#1，则应当持续推进，直至在屏幕上绘制出第一个三角形，随后再加载并显示网格模型，依此类推，不需要关注画面效果的精细程度

 #2 工作的一部分是写一个路径追踪器。路径追踪是电影实现渲染的方式，也是我们尝试借助现代实时渲染技术所力求逼近的目标。开始学习路径追踪的一个极佳起点，是这本名为《Ray Tracing in One Weekend》的在线免费书籍，有很多人已经用过了。内容通俗易懂，并向你展示如何生成照片级真实感的渲染图像。  
[RayTracingInOneWeekend](https://raytracing.github.io/books/RayTracingInOneWeekend.html)

![](Pasted%20image%2020260720154752.png)

#2 的另一部分是学习“基于物理的渲染”或者叫PBR，这是一种应用于光照计算的方法（究其本质，主要涉及高光部分）。PBR 是“基于原理”的渲染方法，意味着只要遵守规则，就会得到好的渲染效果。在 PBR 出现之前，开发者为光照效果编写随机的方程（经验公式），带有各种随意的调整和权宜修补。这种做法只能制作一个在一种情况下看起来很好的资源，一旦改变光照就会使得它看起来太暗，或者会看起来像它在发光。开发者不得不针对不同的光照环境制作不同版本的资源，这无疑耗费了大量的时间与精力。

PBR 使得资源在各类光照条件下均能默认看起来更好，同时省去了为不同场景制作多套资源版本所需的时间与精力。这堪称行业的一个巨大胜利。即便如此，资源创建所消耗的时间，资金与人力，依旧是游戏开发过程中的一个瓶颈。

本页上的 PBR 章节（以及子章节）是一个对 PBR 很好的介绍：
[https://learnopengl.com/PBR/Theory](https://learnopengl.com/PBR/Theory)

![](Pasted%20image%2020260720231612.png)

如果某天已不再满足于上述基础，期望更加深入探究，那么阅读 Filament 的官方技术文档是一个好的进阶。随着对 PBR 的日益深入，将不可避免地涉及大量微积分与统计学知识：
[https://google.github.io/filament/Filament.md.html](https://google.github.io/filament/Filament.md.html)

>译注：Filament是Google 开源的一个高性能 PBR 渲染引擎

在 Filament 文档之上，另一部颇具盛名的著作便是《基于物理的渲染：从理论到实现》（Physically Based Rendering: From Theory To Implementation， PBRT），该书同样提供免费的在线阅读版本：
[https://pbrt.org/](https://pbrt.org/)

理想情况下，你最终会拥有一些你可以与潜在雇主分享的源代码（比如在GitHub上，并链接到简历上），来证明你掌握这些技能。例如：
-  一个看起来大致像引擎的东西，能够加载资源（模型、纹理）并实时将其渲染至屏幕，同时带有光照和一些特效（阴影、景深、面光源、色调映射、光追阴影等）。最好使用 PBR 进行光照计算，带有用户可控的相机，并且使用 DX12、Vulkan 或同类底层图形 API 以及使用 C++ 实现。
- 一个能生成照片级真实感图像的路径追踪器。最好用 C++，但它可以是一个没有窗口的程序，只输出一张 PNG 图片，不需要满足实时。
- 加分项：如果路径追踪器仅仅是你的“类引擎渲染器”的一个独立模式，并通过展示它匹配路径追踪的结果，来验证你的实时 PBR 渲染是否正确（即通过比对两者渲染结果是否一致）。额外加分项：如果能明确指出两种渲染结果不一致之处，并能解释为什么不匹配，并对“如何在保持实时性的前提下，通过改进实时渲染器以缩小两者差异”提出具体思路

你可能会好奇需要掌握哪些数学知识。如果你完成了上述项目，自然会在实践中接触到所需的数学知识，但归根结底，真正需要的不过就是线性代数（包括矩阵乘法、向量叉积点积）、基础三角学以及少量微积分而已。图形学（乃至广义上的游戏开发）的乐趣在于：尽管所需的数学知识极为有限，但能够运用的数学知识却几乎是无限。

算法层面也是这样。应该知道基础的抽象数据类型和算法，例如链表、哈希表、排序和搜索。通常情况下，最快的算法往往也是最简洁的算法，数组在访问效率上远胜于链表。然而，了解更高级的算法概念能在真正需要一些新颖且定制化的算法时提供帮助。

游戏开发领域，C++ 是必学语言，有些人使用 Rust，但该语言的使用率是否增长尚难断言。但Rust 确实占据一席之地，尽管它并非业界普遍期望掌握的标准语言。WebGPU 具备诸多 WebGL 所不具备的功能，且正逐步成为一个更成熟的平台，让你能够使用 JavaScript 处理 CPU 端的相关任务。不过，我很少看到 WebGPU 相关的招聘信息，并且网上也鲜 WebGPU 的内容。就 CPU 端编程而言，掌握 C++ 似乎是目前为止最应该学习的语言。

对着色器语言来说，HLSL 似乎最常用，但也有人用 GLSL。着色器在跨平台游戏中经常被转译到其他着色器语言。

你可能会好奇，成为一名图形程序员是否必须擅长美术，幸运的是，不需要。你将与擅长美术的美术师以及技术美术合作，后者处于程序员和美术师之间，并帮助弥合这两门学科在认知层面上的差异。话虽如此，如果你确实了解一些关于美术、摄影、或类似的东西，那确实有帮助。不过，并非必需。

**关于智能体的机器学习扩展评论：**  
我不认为目前的机ML能够胜任他们宣传的大部分应用场景。我确实通过与 Claude 谈论数学、论文或不熟悉的算法而从中受益。在这种情况下，很容易判断它是否在胡编乱造，也很容易查阅其他来源进行合理性检查。然而，我觉得它在编程方面用处不大，因为即使它完成了预期的任务，我也需要花时间去理解代码。既然如此，还不如自己写。有些小功能我觉得挺有用，比如问“你在这个文件里看到什么bug了吗？”，它要么回答“是”，可以去调查；要么回答“否”，而且问一下也没什么成本。抛开这些技术细节不谈，人类终将在某一天创造真正达到人类水平的通用人工智能，并在此基础上更进一步。我不知道这是否会在我有生之年发生，但我相信它终有一天会发生，除非我们先自我毁灭。从这个角度看，当前的 LLM 时代就像是为未来“真家伙”到来时的彩排，我希望我们能从中吸取正确的教训，并在它到来时做好更充分的准备。
